# 简历话术与面试准备指南

## 一、简历条目（2 条）

> ⚠️ 原则：**没有实测数据绝不写百分比**（"准确率提升 40%"这类话面试官一追问就穿帮）。如果想量化，先自己建 20~30 个问答评测集，跑出真实的命中率/回答质量再填数字。

**条目 1（系统建设视角）：**

> 独立设计并开发「水利知识库智能问答系统」（RAG，GitHub 开源）：基于 Spring Boot 3.4 + Spring AI + pgvector + Redis，打通文档解析（txt/md/pdf）→ 中文段落重叠切片（600 字/100 字重叠窗口）→ Embedding 入库 → Top-K 相似检索 → Prompt 拼装 → 大模型流式生成（SSE）的完整链路；实现 Tool Calling 工具调用、会话级 Redis 对话历史、LLM 调用超时熔断与检索原文降级，Prompt 模板外置化支持热调整。

**条目 2（工程化优化视角）：**

> 针对 RAG 问答的工程化问题做专项设计：以语义完整性与召回空洞的权衡确定切片参数、以相似度阈值过滤 + 系统提示词双重约束抑制幻觉、回答附带引用片段实现来源可溯源、手写熔断器（连续失败→熔断→半开重试）保证大模型不可用时检索链路仍可服务；向量库选型 pgvector 复用 PostgreSQL 运维体系，避免引入独立向量数据库的部署成本。

**GitHub 项目描述（一句话）：**

> 水利知识库 RAG 问答系统：Spring Boot 3.4 + Spring AI + pgvector，支持 SSE 流式输出、Tool Calling、Redis 会话历史与熔断降级，含完整设计决策注释。

## 二、面试官会追问的 10 个问题

### 1. 什么是 RAG？为什么不直接微调模型或用长上下文塞文档？

RAG（Retrieval-Augmented Generation，检索增强生成）：回答前先从知识库检索相关片段，拼进 Prompt 让模型"开卷考试"。对比两条替代路线：
- 微调：成本高（数据标注+训练），知识更新要重训，且容易过拟合、无法溯源。RAG 知识库更新=重新入库，分钟级生效。
- 长上下文塞全文：token 成本随文档量线性增长、超长上下文中间信息利用率下降（lost in the middle），且检索仍然更快更便宜。RAG = 用检索把"必读材料"从全量缩到 Top-K。

### 2. 切片为什么定 600 字 / 100 字重叠？太大太小各有什么问题？

- 太大（>1000 字）：一个切片混多个主题，向量语义被稀释，检索命中时噪声多、回答跑偏，且吃 Prompt 预算；
- 太小（<200 字）：句子截断、上下文缺失，向量语义不完整，召回率下降；
- 重叠窗口：答案正好落在切片边界时，重叠区保证它至少在一个切片内完整出现。
- 加分点：说明参数是可配置的（yml 外置），实际应基于自有文档做网格搜索（300~800 字 × 0~200 重叠）+ 评测集验证，600/100 是工程起点不是终点。

### 3. 为什么选 pgvector？和 Milvus、Elasticsearch 比怎么选？

pgvector：百万级向量以内精度吞吐足够，与业务数据同库（事务、备份、SQL 过滤一套搞定），运维成本最低，团队已有 PG 经验。Milvus：亿级向量、高 QPS、需要独立部署的专用场景。ES：已有 ES 集群且需要 BM25+向量混合检索时顺手。选型逻辑是"数据规模 + 运维成本 + 团队经验"三维权衡，不是谁新用谁。

### 4. 向量检索用的什么相似度？为什么？

余弦距离（COSINE_DISTANCE）。文本 embedding 比的是语义方向而非模长（模长受文本长度影响），余弦相似度只看夹角，对长度不敏感，是文本语义检索的通用选择。pgvector 里的 HNSW 索引把暴力 O(N) 比较降到近似对数级，代价是构建时间和少量召回率损失（可调 ef 参数）。

### 5. 检索质量差（该召回的没召回）怎么优化？

按投入产出排序：
1. 调切片参数和相似度阈值（最低成本）；
2. query 改写：多轮对话中把指代性追问（"那它的校核水位呢"）改写成独立问题再检索；
3. 混合检索：BM25 关键词召回 + 向量语义召回，合并去重（精确术语如站点编码靠 BM25，口语化描述靠向量）；
4. rerank：粗召回 Top-20 → 交叉编码器精排取 Top-5，精度显著高于双塔向量；
5. 元数据过滤：按文件/章节过滤缩小检索空间。

### 6. 流式输出怎么实现的？为什么用 SSE 不用 WebSocket？

后端：ChatClient.stream() 返回 Flux<String>（Reactor 响应式流），Spring MVC 支持响应式返回值，包成 ServerSentEvent 逐 token 推送，事件类型分 sources（引用）/message（增量）/done（结束）。SSE 基于 HTTP、自带断线重连（Last-Event-ID）、Nginx 反代友好；LLM 问答是单向服务端推送，WebSocket 的双向通道是过剩设计，还要额外处理心跳与连接状态。

### 7. Tool Calling 的原理？模型怎么"知道"什么时候调工具？

启动时把带 @Tool 注解的方法的名称、描述、参数 schema（JSON Schema）随请求发给模型。模型判断需要外部数据时，不直接生成答案，而是返回一个"工具调用意图"（工具名+参数）；框架执行本地方法，把结果作为 tool 消息回填给模型，模型基于真实数据继续生成。关键细节：模型决策完全依赖工具描述文本，description 写"什么场景该调用"越具体，误触发越少。

### 8. 熔断降级怎么设计的？降级降的是什么？

手写状态机：CLOSED → 连续失败 3 次 → OPEN（30 秒内所有请求快速失败，不再撞超时）→ 时间过 → 半开放行一次试探（成功回 CLOSED，失败再 OPEN）。降级降的是"生成环节"：RAG 的降级红利是检索结果本身有参考价值，模型不可用时把 Top-K 原文片段直接给用户，服务可用性不至于归零。还会把检索失败（降级为无上下文问答）和生成失败（降级为检索原文）分开处理。

### 9. 对话历史为什么放 Redis？怎么控制 token 消耗？

放 Redis：会话状态是高频读写、可丢失（TTL 24h）、需按会话 ID 隔离的临时数据，和 Redis 的 List+TTL 天然匹配；数据库持久化对话价值不大（还没做多设备漫游）。token 控制：LRANGE 取尾部、窗口裁剪（最多 6 轮 / 40 条），只把最近 N 轮拼进 Prompt，且历史和知识库上下文共享预算——这是多轮 RAG 的核心矛盾，可扩展为"历史摘要压缩"。

### 10. 大模型幻觉怎么缓解？

四层防御：
1. 检索层：相似度阈值 0.4，低相关片段不进 Prompt（噪声是幻觉主要诱因）；
2. 提示层：系统提示词明确"严禁编造知识库不存在的内容、找不到就明说"；
3. 溯源层：回答要求注明来源文件名，SSE 先推 sources 事件，用户可核对原文；
4. 降级层：知识库没内容时明确告知，而非让模型裸答。
诚实加分点：RAG 只能显著缓解不能根除幻觉，Prompt 约束是概率性的；对数值精度要求高的场景（水利调度）最终仍需人工复核关键数据。

## 三、面试加分动作

- 现场演示：上传文档 → 提问 → 指出回答里的 sources 引用 → 再问"实时水位"看工具触发；
- 主动讲一个踩坑：比如 ST4 模板对大括号敏感、DashScope 兼容模式没有 DeepSeek 的 embedding 接口这类真实细节；
- 被问到没做过的扩展（rerank、混合检索）时说清原理和"我为什么还没做"（Demo 数据量用不上），比硬编经历可信得多。
